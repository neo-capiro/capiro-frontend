# Portfolio P3 cohesion review — Calendar and Relationships

Date: 2026-10-11. Reviewer: Codex `portfolio_calendar_relationships`.

## Result and scope

The TypeScript AST scan found **49 size signals in 125 authored modules**: 48 function bodies over 80 nonblank lines and one file over 400 nonblank lines. Each affected module was read, and each function was assessed separately. **45 functions retain a cohesive responsibility. Four signals remain pending extraction**, representing three components: `TranscriptForm`, the `MeetingPreparation` module / `ScopedPreparation`, and `MailCompose`. These pending findings are not approved by this review.

The canonical source roots are `apps/web/src/features/portfolio/calendar` and `apps/web/src/features/portfolio/relationships`. The inspection began before the mechanical app move and was rescanned against those canonical paths afterward. Imports were relocated by root; this review adds no source reorganization or shared framework.

Size is a review trigger, not evidence of either correctness or poor cohesion. The retained decisions below state each function's responsibility and where adjacent behavior already lives. Optional future extractions are tied to concrete growth or reuse; none is a blanket exception for JSX or legacy code. The new `CommitteePickerPanel` was reviewed by its author here; root should independently confirm that particular ownership judgment before integrating its exact record.

## Method and reproducible evidence

The repository's `scripts/architecture/scan.mjs` supplied the findings. Function line counts use the nonblank lines in the AST function body; fingerprints cover the whole function node, including its signature. A file fingerprint covers the full source. Fingerprint normalization replaces CRLF with LF and trims outside whitespace before SHA-256. No regex-only function count or path wildcard approval was used.

## Concrete extraction findings

### Meeting preparation: extract a status view, preserving the run controller

`MeetingPreparation.tsx` has 404 nonblank lines; `ScopedPreparation` has a 343-line function body. The parent currently renders two separately changing views: durable preparation job progress/recovery and the saved document with actions, editor, settings and sources.

The minimal proposed boundary is **`PreparationRunStatus`**, a render-only component in the existing preparation folder. It should own the visible pending/current-job/terminal status sections, progress explanation, same-request retry button, explicit refresh button and their error/status messages. It should receive typed state and callbacks from `ScopedPreparation`.

Keep capability/readiness checks, current authority, `requestKey`, busy/can-generate decisions and the existing mutation hooks in `ScopedPreparation` initially. The extracted view must neither create a new job nor derive a new request key. Same-request retry must keep its existing identity; refresh must remain an explicit read. Keep the institutional readiness gate and saved-document actions in their current owner. This is a proposal only; no source extraction was authorized in this lane at the time of review.

Before implementation, characterize the existing pending, active, failed/cancelled/completed, same-key retry and refresh cases in the dedicated meeting-preparation tests. Extract the status responsibility as a whole, then re-read both modules. Renaming the monolith or carving arbitrary 80-line chunks would not address the finding.

### Transcript source: move the attempt out of the form

`TranscriptForm` has a 221-line body. Alongside file and preview controls, it owns upload attempt refs, a scoped API wrapper, confirm/extract sequencing, retry phase and query invalidation. A **`useTranscriptSource`** controller can own that single attempt and expose typed stages, retained receipt, error and run/retry commands. If the ordering still dominates the hook, a small transcript-specific preparation adapter can hold that sequence.

Reuse `uploadParentFile`, `extractMeetingSource` and the existing authority/attempt contracts. Keep file input and reviewed text in the form. Voice and transcript workflows already have different retry/unknown semantics; do not merge them simply because both accept a file. This extraction is a pending recommendation, not implemented or approved as completed.

### Mail composition: source-bound rewrite controller

`MailCompose` has a 288-line body at inspection. It includes an asynchronous rewrite request and HTML-to-plain-text conversion in the compose UI, as well as frozen send-review presentation. A concrete bug accompanies the responsibility overlap: a late rewrite response unconditionally calls `setBody`, replacing a newer manual draft.

Root authorized the bounded rewrite correction after the mechanical move. The implementation outline is to extract the existing rewrite operation into a specific controller, keep its native request/response contract, capture the actor/client/recipient/thread and draft identity, and discard a result whenever that source or composer lifetime no longer matches. An `AbortController` should stop local response handling on draft/context replacement or unmount. This must not claim that server-side model work was cancelled. Existing mail authority should be rechecked immediately before applying a response. HTML conversion belongs at this rewrite boundary rather than in JSX.

Verification should hold an intercepted response while the body changes, close and reopen the composer, and invalidate/change identity. The current draft must remain intact, stale content must never appear, and no send request may occur. A current unchanged draft should still receive a verified rewrite; unverified results must preserve the original draft and show the existing warning. Original compose/send/attachment assertions must remain. A render-only `ReviewedMailDialog` is an optional later extraction if its frozen-intent presentation continues to grow; sending remains in the canonical send owner.

## Rewrite follow-up after the initial review

The authorized rewrite extraction is now implemented. `email/useMailRewrite.ts` owns the composer source, draft revision, captured native mail authority, local cancellation and result application. `email/rewrite.ts` owns the unchanged request/response boundary and plain-text conversion. `MailCompose` supplies the current client/contact/thread/recipient context and presents state. A draft edit increments a revision even when the text returns to its earlier value. Context changes forget the old pending status even when recipients are later restored. Unmount and identity invalidation abort local response handling; server-side cancellation is not inferred.

This resolves the specific mixed responsibility previously recorded for `MailCompose`. The current `MailCompose` body is 272 nonblank lines and is retained as one draft/review composition. The new `useMailRewrite` body is 110 nonblank lines and is retained as one coupled attempt lifecycle, using the existing mail authority instead of a parallel policy implementation. Both exact post-change records and their substantive reasons are in `architecture-rewrite-reviewed-records.json`. The original 49-finding inspection evidence is preserved. The current inventory adds the new controller: **50 signals, 47 retained function records, three pending signals** across `TranscriptForm` and `MeetingPreparation` / `ScopedPreparation`.

The focused new transport tests and original compose unit suite pass together: 32/32 across two files. The new browser specification contains nine intercepted regressions for current verified/unverified results, edits and edit-back, old/new attempt ordering, close/reopen, recipient change/restore, identity invalidation/actor change and pre-dispatch refusal. Browser results remain pending root's integrated run at this checkpoint. No original browser assertion was removed. Root should independently review the new controller before adopting these author-reviewed records.
