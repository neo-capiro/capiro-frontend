# P6 capability and opportunity current-read continuation

## Implementation outline — 11 October 2026

This bounded continuation starts at `ee39c2fc6e3520ac5e9eb49cd9b8a6d94e6716eb` in the isolated `codex/portfolio-current-reads-20261011` worktree. It repairs retained frontend guards for CAP-01/02/03/04/10/11 and OPP-01/03/06, supporting OPP-02. Existing `capirov2` endpoints and response schemas remain authoritative. No new client echo, version, idempotency key or backend service is introduced.

- Capability and fit query hooks own reads; their components render list counts, records, links and editors only after the corresponding successful read. A failed list read must not conceal a separately successful fit read.
- A capability writer module will own request parsing, exact edited-record receipt validation and guards around transport. A capability mutation module will own the captured actor, client, selected record, view lifetime, single-flight dispatch and guarded cache/callback effects. It will reuse the shared current-client-writer and HTTP client owners.
- The Opportunities page will gate each feed and its derived summary, pagination and detail links on that feed's current result. One failed feed must not remove the independently successful feed.
- Dedicated browser fixtures use real feature components, the real provider and synthetic local responses. They reproduce cached-success then failed-read transitions and delayed mutations across identity/context/unmount changes. Pure writer tests cover receipt and transport boundaries. Existing behavior tests are retained.

## First source checkpoint: 32 browser cases pass

The assigned current-read and capability execution repairs are implemented. The browser uses the same existing endpoints, request bodies and response fields. Capability create accepts the existing generated record identity; edit requires the exact requested capability ID. Neither the capability nor fit receipt supplies a client echo, and this change does not invent one. Delete retains the existing acknowledged/204 response semantics.

`queries.ts` now owns reads only. `writer.ts` owns validated capability/fit transport and guards before and after the request. `mutations.ts` captures the current client writer, selected record and mounted view; it aborts when that scope or identity becomes invalid. It checks the actual identity query state, including invalidation without refetch. The editor shares one save/remove operation and disables its fields while a request is pending. Cache invalidation and editor callbacks run inside the captured operation rather than a later, potentially changed `onSuccess` closure. An acknowledged removal closes while its selected editor still exists, before the refreshed list removes that editor. Fit computation cannot overwrite a newer fit read, a failed fit read or an invalidated/in-progress read.

Each page derives records and counts from the corresponding successful read. The capability editor unmounts when its source list fails and starts from current data after retry. Fit read errors remove retained targets, evidence, computed counts and links; a failed computation keeps an independently successful fit read available, as shown in Figma `411:55097`. Opportunity and PE feeds remain independent. A failed feed loses its rows, derived summary, pagination and feed links, while the other feed remains available. Retrying successfully restores the current result. Header handoff links follow the same successful-feed gate.

The extension's implementation outline keeps registration form fields and the read/display state in the capability feature, with a guarded registration transport/mutation owner. Inspection of the installed Query 5.104.1 source and the captured HTTP trace showed that the library itself sets `isInvalidated:true` when that read fails, before the held PUT is released. The corrected assertion compares the complete failed/replaced query state before and after the receipt; it retains the no-extra-cache-effects requirement. The trace showed only the initial GET, denied GET and held PUT, without another client or fit read. That first run is preserved separately in `browser-registration-first`.

The synthetic harness now uses Query's `notifyManager.batchCalls` for its cache probes, matching the library's observer scheduling. A query created when the real registration component mounts otherwise synchronously notified the harness during child render. This is a fixture-observer correction; it does not change product mutation timing or bypass a boundary. Both registration visual cases explicitly reject that React render warning.
