## Findings and dispositions

### 1. Resolved: pure validator imports traversed a runtime barrel

At the feature checkpoint, `prospects/contracts.ts` imported `safeWebsite` through `index/public.ts`. That barrel also re-exports `index/queries.ts`, which imports the React/Next API provider. A new Playwright spec importing the otherwise pure prospect catalog through this chain failed during Node test collection at `next/link` resolution, before browser tests began. An explicit independent server fixture corrected the test, but initially left the production import coupling in place.

Root resolved the finding by moving the single canonical validator into `apps/web/src/shared/portfolio/domain/website.ts`, retaining compatibility re-exports through `index/contracts.ts`, and importing the pure owner directly from the prospect contract, CSV model and meeting link consumer. This review caught the remaining mixed value/type import in `client-intake/form.ts`; root then split its `Client` type-only import from its direct `safeWebsite` import. The intake form no longer resolves a query/provider module merely to validate a website. This uses an appropriate shared domain owner without copying the validator or accessing another feature's private module.

The corrected imports were inspected on 2026-10-11. A direct Node import of `shared/portfolio/domain/website.ts` passed five checks covering a bare host, an HTTPS path/query, credential rejection, unsupported-protocol rejection and a null input. It imported without React/Next resolution. Existing URL-validation suites remain part of root's integrated run. The original finding was import cohesion, not evidence that the browser application failed to load; the pre-consolidation affected browser batch passed all 42 cases.

### 2. Enrichment mutation lifetime also owns result wording and cache fan-out

`client-profile/enrichment/useReviewAction.ts` keeps session lifetime, abort behavior, ambiguous dispatch state, action-specific result text and finding-kind-specific cache invalidation in one hook. The first three belong together. Result presentation and the set of affected projections can change independently when a finding kind or an existing projection changes.

A concrete extraction is an enrichment-local typed module that derives the acknowledgement text and affected query keys from `ReviewAction`, the reviewed run and the returned run. Keep dispatch, actor checks, uncertainty and timing in `useReviewAction`; keep HTTP and receipt validation in `executeReviewAction`. Reuse deliberate public query-key exports where available. Avoid a generic cross-feature mutation framework, and preserve invalidation after partial or ambiguous apply outcomes. This would make a new finding kind change the projection rules without expanding the authority/lifetime hook.

The current hook is retained for the mechanical migration because it still controls one review mutation lifetime and already delegates transport. The extraction should precede further action/finding-kind growth; this review does not approve adding more branch families to the hook unchanged.

### 3. Specific presentation sections can be separated without splitting state ownership

The clearest view-only seams are the conflict comparison in `BriefEditor`, the repeated controlled contact fields in `ContactEditor`, and the selected-logo input/status block in `IntakeSession`. Their useful boundaries are a version-pinned comparison view, a contact field view with validation/focus wiring, and a logo-selection field respectively. They should receive controlled values and callbacks, not acquire their own network or mutation state.

The current editors retain the state that must remain coupled: original versus reviewed brief versions and frozen save attempts; a contact's expected version and creation request identity; and a saved client plus a pending logo attempt. Extracting these state machines into generic helpers merely to lower line counts would make replay and recovery behavior harder to assess. The existing separate validators, three intake step components, mutation hooks and upload transports are meaningful divisions already in place. Prefer one of these named view extractions when that section next changes; do not perform a wholesale editor framework rewrite.
