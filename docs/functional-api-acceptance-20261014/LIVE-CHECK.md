# Short functional-preview check after deployment

This sequence is for Neo's existing account and tenant after shipping verifies the existing preview frontend's image and configuration. It does not require the 337-row native ledger to pass. Record each step as passed, failed or unrun; a missing candidate endpoint is a feature dependency, not a reason to block otherwise working preview login and ordinary reads.

1. **Login and identity.** Open `https://portfolio-preview.app.capiro.ai` and sign in through the existing Clerk flow. Use Neo's existing account and organization; confirm `/me` resolves the intended existing tenant and normal role. Record the deployed image/source and ordinary response statuses without tokens or secrets. Ordinary login metadata updates are accepted. Do not sign up, create an organization, impersonate another user or test another tenant. If the host needs an access change, shipping must identify the exact change for approval.
2. **Known client and navigation.** Find and open one already accessible client. Check list/search, profile, refresh and browser Back/Forward. Navigate Portfolio → Meri → Modules → Settings through the shared header. Meri may show its existing unavailable/synthetic state; do not run it. If Neo already has a second accessible client, switch to it and confirm the header/data/editor context changes, then return. Do not create a client: the existing creation route can trigger entity resolution, prepopulation and configured SAM enrichment.
3. **Missing-contract feedback.** Read Objectives and open Manage owners. If their current source returns 404, confirm a visible unavailable error, no false empty list/assignment, no enabled dependent save and no success receipt. Open master Agenda, confirm any effective-date source failure is visible while available feeds remain usable, then return to Month. Distinguish 401/403/configuration/network failures from 404 in the observation. Do not start ingestion, repeatedly attempt writes or infer record deletion from 404.
4. **One optional ordinary write, using only a new manual draft.** In Modules → Workspace, choose **+ New document → Newsletter → Start blank** (the Code your own category if the template picker requires it). Use a unique title such as `Preview check <UTC timestamp>`, plain manual text, no template generation and no client link; use the existing firm scope. Save once, record the newly returned draft/document/version IDs, reload and read back that new draft. Modify only these newly created test records if a correction is needed. If the result is uncertain, stop and inspect the new draft by its exact ID/title; do not blindly repeat creation. Leave it for Neo to review rather than deleting it during the smoke check. Skip this step if the existing role cannot create a draft, the displayed flow differs from the reviewed manual path, or the chosen item is an existing business record.
5. **Session and basic interaction.** Sign out, use Back and confirm protected data/editors cannot continue writes; sign back in as the same account. Observe normal session expiry only if it occurs—do not administratively revoke/change access. Check the same navigation on desktop and mobile, keyboard focus, dialog dismissal and announced error/status text. This bounded check does not claim complete Figma or accessibility acceptance.

Do not stage into Outreach, send/share/provider-connect, generate with Meri/AI, enrich/sync, upload/export, bill, change permissions, overwrite existing documents or restore/delete existing records. A failed optional write does not erase successful login/read evidence. Report the exact route/status and affected action instead of broadening access or guessing an endpoint.

## Why the manual draft is the bounded write candidate

The frontend's existing `use-newsletter.ts` manual save performs ordinary Workspace operations: `POST /workspace-api/drafts`, `PATCH /workspace-api/drafts/:draftId/documents/:documentId`, `PATCH /workspace-api/drafts/:draftId`, then `POST /workspace-api/drafts/:draftId/versions`. The first creates the new draft/document; the later writes affect that new record and save its revision. No staging endpoint is part of this path.

Read-only inspection of `capirov2@4be13b0b1ed0f2f3fa014040eedbb2fc2c27dace` found direct database create/update/snapshot operations with the existing access checks in:

The inspected methods do not start an agent, enrichment or external provider. Restore is a different destructive operation and is excluded. This source assessment does not prove the deployed backend is the same revision; record the deployed service/source if available and stop if live behavior differs. No live draft or API call was made in this frontend repair session.
