This is **static source acceptance only**: author tests are pending, no tests were run by this reviewer, and no UI or native lifecycle is accepted. Two concrete issues were found on the first read and corrected by the root during review:

1. `stageDetail` and `record` originally spread the caller's mutable `expected` object after awaiting the response. A caller could change expected document/client/revision while the request was pending, admitting a response against the replacement expectation. They now capture `requested` before dispatch and bind the response to that snapshot. The new held-response controls mutate the caller's original expected fields to match a foreign receipt, then require rejection against the original fields. These are meaningful regressions by source inspection; their execution is not claimed.
2. The positive stage fixture originally used `/modules/engagement?newsletterStageId=...`, which the public parser correctly refuses. This also made the document/revision negative cases fail before their intended mismatch. The fixture now uses exact `/engagement/outreach?newsletterStage=...`; the positive and negative cases can exercise their intended checks.

The initial disk snapshot was captured after correction work had begun. It is explicitly an intermediate snapshot, not a failing baseline. No synthetic failure or reconstructed original source has been substituted for an unrun test.

Additional source corrections are verified: the duplicated Core UUID regex was replaced with the existing `richNewsletterId`; Workspace parameters use Zod UUID validation plus a v1–8 refinement to exclude nil/all-ffff sentinels that installed Zod otherwise accepts. - The single `receiving` transform adapts producer-owned parsing to the existing Zod gateway/browser slot. It propagates validated public output and a bounded error. There is no copied response DTO, guessed data wrapper, private package import or unchecked response cast. The Core request syntax reuses its existing local owner; the public package exposes no separate ID-schema export.
- The semantic adapter binds document detail to requested document/client; save to captured submission/document/client and nominal incremented revision; stage-create to document/submitted revision; stage/record reads to captured expected fields with requested ID overriding any extraneous caller property. Save captures the body before dispatch. List/create correctly do not invent IDs or selected-client ownership; list retains server-authorized documents from other clients.

The adapter introduces no retry, readback, record creation, navigation or effectful collaborator. Preview is explicitly saved HTML without an ID/revision receipt; no authority is inferred from it.
- Existing `createCapiroApi` owns request validation, same-origin credentials, scope abort and response parsing. The adapter preserves supplied abort signals and relies on that existing transport. It neither replaces shared session/client lifetime nor creates an alternate cache or authorization system.
