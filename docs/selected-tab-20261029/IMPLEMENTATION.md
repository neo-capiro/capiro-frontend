# Selected-tab attachment consumer

The composer can connect to the selected-tab browser extension prepared in Meri
Runtime351. The parent delivered its public receiver through Runtime352 and
Frontend317: installed contracts 0.1.31 and ui-stream 0.1.18. Production code imports
only `@capiro/meri-contracts/selected-tab-application`.

## Ownership and behavior

- `shared/meri-selected-tab/chrome-port.ts` opens a native Chrome external port to
  the deployment's exact extension ID. It accepts no window-message relay or URL.
- `SelectedTabAccess` binds that connection to the current native conversation,
  account, client and session lifetime. The canonical receiver validates closed
  messages and exact UTF-8 bytes/hash. Pair/device identity, capture age, scope,
  pause revision and one-use selection checks precede the upload handoff.
- `SelectedTabUploads` associates a selection with the request ID generated by the
  existing upload owner. It keeps no second receipt ledger, credential or writer.
  The existing upload controller owns declaration, original storage, Check status,
  removal and the eventual conversation attachment argument. A storage receipt
  does not claim scanning or extraction success.
- `shared/meri-conversations/port.ts` composes the existing conversation resources
  under the same admitted session. The host still owns issuance, account matching,
  context binding, renewal and access loss. Resource composition was extracted
  from its constructor without changing those responsibilities.
- `features/meri/selected-tab` displays current account/scope labels from `me.read`
  and connects, pauses or disconnects. Labels are display text, not authority.
  Native lifetime loss, UI unmount, expiry or malformed/foreign messages close the
  connection. Pause cancels only this connection's pending uploads. Stored files
  remain controlled by the attachment owner.

The optional public deployment setting
`NEXT_PUBLIC_MERI_SELECTED_TAB_EXTENSION_ID` must contain the installed extension's
32-character Chrome ID. Missing/invalid values hide the control. No value is set by
this change. The extension's `externally_connectable` origin must also match the
application deployment; configuring this ID alone cannot grant access.

## Upload cancellation correction and structure assessment

The existing controller briefly had no cancellable attempt when it published its
declaring state and between declaration and original storage. A synchronous pause
at either notification could therefore fail to prevent the original write. Two
tests demonstrated both failures before the fix. One controller-owned attempt now
exists before the declaring notification and spans both stages. Its cleanup only
removes its own current controller. No new retry or effect authority was added.

`createUploadController` remains a size-review signal (295 nonblank lines;
fingerprint `8191d6f6593565d12a0bbd846e7925ab0aba62e33a83f0b89d26a025028c85e1`).
Author assessment: it owns one conversation's attachment state and selection,
with the existing wire retaining receiving/transport and the existing ledger
retaining receipts. `storeOriginal` names the cohesive two-stage upload procedure;
the optional `onStarted` callback exposes only the owner-generated correlation ID
before dispatch. Splitting this state across another selected-tab controller would
duplicate effect ownership. The new selected-tab, conversation-port and extracted
host modules introduce no size signals. This is an implementation assessment,
not an independent review; the user's review hold remains in force.

## Qualification and remaining acceptance

Focused tests exercise the installed public package, the real upload access and
conversation host. They cover exact bytes, foreign scope/device/pair, stale or
altered capture, duplicate share, pause races, native expiry and status-only recovery
after a lost storage acknowledgement. Chrome component checks exercise the real
composer, identity query, native-port connector and upload owner with explicitly
synthetic extension/service endpoints, including keyboard access and narrow layout.

These checks do not qualify an installed extension, extension permission prompts,
its popup, authenticated end-to-end upload, deployment or restart durability. The
existing upload ledger is in-memory for a native session: reload/session replacement
does not recover unsubmitted upload attempts, and a lost declaration acknowledgement
without an allocated upload ID has no status lookup. No second recovery store or
automatic replay is introduced. These remain acceptance gaps, not a completed A4
capability. No app/image build, deployment, provider call or independent review ran.
