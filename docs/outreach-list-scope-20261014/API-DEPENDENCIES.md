## Minimal saved-layout requirements for the backend owner, through the parent

This is a **separate genuinely missing receiving contract** according to the exact backend-owner map, not one of the four existing families. The frontend already has its deliberate adapter and unavailable behavior; no second store or frontend persistence fallback is warranted. Please bind/implement the agreed canonical persistence owner and return its exact source/controller mount/config/migration/test mapping.

1. Existing frontend route expectation: authenticated Core **GET/PUT `/api/me/portfolio-layout`**. Trusted tenant and user come from the existing server session, never browser-supplied actor fields. Existing frontend writer admission allows standard_user, user_admin and capiro_admin; backend role/membership policy remains authoritative and must be qualified.
2. GET and successful PUT must return the strict JSON receipt `{ contractVersion: 1, tenantId: UUID, userId: UUID, version: integer 0..2147483647, updatedAt: ISO datetime | null, order: string[] }`. Extra receipt keys are currently rejected. Exactly `version === 0` means `updatedAt === null`; a persisted positive version requires a timestamp. Each order token is lowercase `client:<UUID>`; tokens are unique, at most 2,000. Tenant/user echoes must match the current identity.
3. The returned order must contain **exactly the full current accessible non-archived profile catalog**, once each, not the visible search/owner subset. Empty catalog means `[]`. Reject foreign/walled/archived/nonmember tokens. GET must reconcile catalog changes before returning; document deterministic new-card/removal ordering and any version change caused by reconciliation so concurrent catalog changes do not silently overwrite intent. The frontend validates set equality with its current catalog and requires reload on disagreement; it cannot choose this server policy.
4. PUT body is exactly `{ contractVersion: 1, expectedVersion: integer, order: string[] }`. Current frontend accepts expectedVersion 0..2147483646. Perform atomic version and current-catalog/membership validation with durable per-tenant/per-user storage. Successful response must have **version `expectedVersion + 1` and exactly the submitted order**. Initial save must be supported from version 0. Decide/version-document overflow handling; do not return an ambiguous success or silently increment by another amount.
5. A stale version is HTTP **409**, with no accepted replacement. Frontend explicitly rereads and reviews the latest order before another user-selected save. 401/403/404/503 remain ordinary denied/unavailable responses; never substitute a success/empty catalog for unavailable service or authorization failure. PUT must not automatically replay after interruption. Following an uncertain response, GET must reveal the durable version/order: the frontend resolves success only when both match the original expected+1 and exact original order; otherwise it requires review.
6. Supply the real mounted Core route, session/membership guards, persistence/schema owner and allocated migration path, plus positive initial/read/save/readback, wrong actor/catalog, catalog churn, stale-CAS/concurrency, revocation, restart/lost-response durability and role/tenant isolation checks. A historical unregistered candidate or local test is not deployed availability. No schema application, live write, new store or permission change is authorized by this frontend handoff.
