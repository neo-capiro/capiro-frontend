## Selected-client read target: source compatibility before routing

The qualified Core PR #48 image at `6542f5b089656b6d255465edd464d06c2a0b408f` contains ordinary `GET /api/me` and `GET /api/clients[/<id>]` handlers, but its current preview listener forwards only named POSTs and the independent priority-3 guard returns 404 for these GETs. A listener change alone is **not** evidence that the frontend's reviewed read-source binding is served: Core commit [`111f269d749cae0249c2141779bd6d7deb93f45c`](https://github.com/neo-capiro/capiro-backend/commit/111f269d749cae0249c2141779bd6d7deb93f45c) is on a separate branch, not an ancestor of the qualified PR #48 image. Its [read-only API handoff](https://github.com/neo-capiro/capiro-backend/blob/111f269d749cae0249c2141779bd6d7deb93f45c/docs/preview-readonly-api-20261013/HANDOFF.md) specifies an isolated entrypoint, a restricted read-only database identity, an existing active `capiro-internal` membership and only the three GET paths. It has no qualified/deployed read image or host in this frontend handoff.

That isolated Core process uses `node apps/api/dist/src/preview-readonly/preview-main.js`, not the ordinary PR #48 `serve` entrypoint. Its source requires `CAPIRO_PREVIEW_READONLY=true`, `PREVIEW_READONLY_DATABASE_URL` with a separately approved effective read-only role and `default_transaction_read_only=on`, `PREVIEW_TENANT_ID=<verified UUID>`, `PREVIEW_CLERK_ORG_ID=<verified org ID>`, and matching Clerk secret/issuer. Those are **Core-owner runtime inputs**, not extra frontend task variables. The Core owner must verify them through native database and identity checks before supplying a read host.

The read-only controller has no `/health` route in its exact allowlist; a target group cannot assume an ordinary HTTP health path. Core's owner must review a bounded liveness mechanism without broadening its business route allowlist. Its client list excludes archived clients by default, while detail may return one; choose an active, currently visible client that the Core bootstrap also accepts.

The source-consistent routing choices for Core's owner and Fable are:

1. **Preferred for the unchanged frontend image:** qualify the separate `111f`-derived read-only Core runtime with its native tenant, Clerk, database, image, HTTPS target and exact three-path listener/deny guard. Bind its approved `/api` host as `CAPIRO_PREVIEW_READ_API_BASE_URL`. This preserves the qualified frontend source marker and the Core first-chat POST service as separate targets.
2. **Shared hostname, separate read target group:** the frontend validator permits the read target and bootstrap target to share `https://first-chat-preview.app-dev.capiro.ai/api`, but exact GET listener rules must forward to a separately qualified `111f` read-only process, while POST bootstrap continues to the PR #48 target group. Move the retained host-only 404 guard below every reviewed narrow forward and above the host-agnostic production rule, with fresh priority inventory and no broad method/path Cartesian-product rule. This is a larger listener change and still requires all `111f` native/image/role proof.
3. **Consolidated Core runtime:** review a new Core source that serves the equivalent isolated read contract alongside bootstrap, including the read-only authority boundary and a safe listener order. Its new source identity must be reconciled with the frontend read marker. Changing the frontend marker or read behavior changes product source and needs a separately reviewed frontend image qualification; the existing `e0b47a34` image cannot attest those new bytes. Do not point `111f` at ordinary PR #48 GET handlers solely by adding an ALB rule.

The qualified frontend [GET adapter](https://github.com/neo-capiro/capiro-frontend/blob/e0b47a34d00b8c181420188ed39a1d849e25ec0a/apps/web/src/shared/preview/read-proxy.server.ts) sends the native Clerk bearer and fixed `X-Capiro-Tenant: capiro-internal`. Consequently the no-rebuild path is scoped to a **verified authorized `capiro-internal` tenant**, its designated Test Clerk member and one selected client owned/visible there. Core bootstrap, the read service and Meri must agree on that tenant, actor and client. A different Test tenant cannot be fixed by a target URL or flag; it requires owner review of the tenant contract and a newly qualified frontend image if its adapter changes.

There is also an unresolved Clerk source mismatch: the frontend preview proposal validates a Test Clerk issuer under `*.clerk.accounts.dev`, while [Core's held service source](https://github.com/neo-capiro/capiro-backend/blob/8ea7acc85793402984a59a308100d64b88b5876b/infra/cdk/lib/preview/first-chat-core.ts) fixes `CLERK_JWT_ISSUER=https://clerk.app.capiro.ai` and an existing dev secret reference. The `111f` read-only packet calls for the existing Clerk secret and exact issuer. No current receipt proves that the frontend's proposed Test credentials produce a native bearer accepted by both Core runtimes. Fable and the Core owner must select and verify one authorized Clerk application, issuer, token template and actor/tenant mapping before enabling the gates; do not silently exchange secret references.

## Meri contract version: consumer and producer are different facts

The qualified frontend's `apps/web/package.json` and lockfile install the accepted `vendor/capiro-meri-contracts-0.1.8.tgz`, SHA256 `0b0dffa63e19c55a3bc91e0c6b39cd5ad5916c6941ae1ccdc92098ba580d9820`, Git blob `cbd7cd8246fee5feef17a1119dc93e66df06a5a6` in the image source. The [route gate](https://github.com/neo-capiro/capiro-frontend/blob/e0b47a34d00b8c181420188ed39a1d849e25ec0a/apps/web/src/shared/preview/meri-conversation-route.server.ts) calls `0.1.8` **the app's pinned distribution**; its environment value must match those frontend bytes. It does not establish a Meri producer package version or wire compatibility by itself.

Meri [PR #101 at `38f52df94b1738649776792b2a28aac743801c19`](https://github.com/neo-capiro/meri-greenfield/blob/38f52df94b1738649776792b2a28aac743801c19/packages/contracts/package.json) still labels its public `packages/contracts` distribution **`0.1.7`** and omits the public `conversation-initial-input` export. Do not relabel that manifest or any image as `0.1.8`. The accepted frontend `0.1.8` tarball is additive against the retained `0.1.7` tarball: 34 of 35 old regular package members are byte-identical; the only changed old member is `package.json` (version/exports), four new members are generated `conversation-initial-input` declarations, metadata, receiver and schema, and none were removed. The existing `conversation-input` admit contract remains at its own `0.1.7` metadata version.

The new initial-input contract declares `POST /api/conversations/input/allocate`, schema `urn:meri:conversation-initial-input:1.0.0`, 131,072-byte request/response limits and separate `NOT_DISPATCHED`/`UNKNOWN` recovery outcomes. Its request reuses the canonical conversation-input request shape; the new strict success response carries an allocation (binding, scopes, versions, selected client, request/input hashes and expiry), `state` (`RESERVED` or `ACCEPTED`) and `created`. Meri PR #101's `apps/runtime/control.mjs` imports the private initial-input protocol and mounts its allocation application on that public path; its private protocol declares package version `0.1.8`. Read-only hash comparison of the tarball's provenance metadata against exact PR #101 Git bytes found **21/22 distinct source paths equal**, including initial-input HTTP, journal, store, service, migration, protocol, semantics and prior generated conversation contracts. The sole missing path is the package generator `packages/contracts/generate-initial-input.mjs`, so this is strong runtime wire-source correspondence, **not** a claim that the full `0.1.8` public package can be rebuilt from PR #101. Counting its duplicate matched `browserImports` record yields 22/23 matching pin entries.

The smallest truthful no-frontend-rebuild option is to keep the frontend consumer value `0.1.8`, record Meri's producer manifest as `0.1.7` and independently verify the exact Meri image source/digest, mounted allocate/admit behavior, native authentication, request/response shapes and recovery before activation. Source correspondence does not replace those live checks. If the release policy requires identical **producer and consumer public package versions**, Meri must publish and qualify a genuine `0.1.8` package/source successor; changing only an environment string or package label cannot satisfy that policy. The frontend's `0.1.8` provenance gate must not be weakened to `0.1.7` to make the current image pass.

## Minimal deployment-source delta and readiness order

The qualified frontend already contains the narrow GET, bootstrap and Meri route gates. No frontend product-code change or duplicate image build is needed **if** the isolated read contract, internal tenant and Meri contract are qualified as above. The checked-in `apps/web/deployment/portfolio/service.yml` currently emits none of the new `CAPIRO_PREVIEW_*` or `MERI_FIRST_CHAT_*` variables; `preview-config.mjs` cannot validate a full candidate containing them. Fable should prepare a narrow deployment-only template/validator delta with explicit held defaults, exact source/target/client parameters, and rules that reject enabling any route before its required binding is present. Reconcile every then-current stack parameter and the live task definition; the checked-in template's ordinary URL allowed values do not match the currently deployed `os.capiro.ai` bindings. A blind template apply or `UsePreviousValue` would carry an unreviewed production-bound target.

Before any activation, require owner receipts for: (1) Core first-chat service health and native identity plus the `c64f` contract ancestry; (2) a separately qualified `111f` read runtime, exact GET route/deny behavior, native bearer, `capiro-internal` tenant and read-only DB authority; (3) Meri image source/digest, HTTPS origin, startup health, Core identity/context verification, selected client, database/migration, model/custody and Temporal readiness; (4) designated Test Clerk/hostname/ingress and an inspected listener-priority allocation. Core's existing priority-3 retained 404 guard conflicts with an older Meri priority-3 proposal. Only the shipping owner should prepare and execute a reviewed preview change set after coordination; dot then runs the live checklist. No image build, AWS mutation or activation is part of this plan.
