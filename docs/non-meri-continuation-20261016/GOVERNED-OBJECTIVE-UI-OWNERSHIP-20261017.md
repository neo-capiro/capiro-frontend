## Current frontend and Core seams

The existing `ObjectiveGeneration.tsx`, `objective-generation-session.ts`, `objective-generation-recovery.ts`, `objective-plan-session.ts`, and `ObjectivePlanOutcome.tsx` implement the earlier Objective draft-job and Planner materialization flow. `shared/capiro/operations/objective-generation.ts` calls the legacy Strategy draft-job API. `strategy-materialization-semantics.ts` requires created project and task counts to equal output counts. Preserve that decoder for its current wire contract; canonical v3 may retain output IDs and needs a separate receiving contract.

PR #53 includes these authenticated, `private, no-store` Core routes in its [controller](https://github.com/neo-capiro/capiro-backend/blob/57f8c8047a73df6d4a73351a98a5239f38240a24/apps/api/src/clients/objectives/work/objective-work.controller.ts), under the application's existing `/api` prefix:

| Operation | Route and input                                                                                                                                             | Frontend use                                                                                                                                                                     |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Observe   | `GET /clients/:clientId/objectives/:objectiveId/generation?workAction=objective.plan.prepare` or `objective.strategy.draft`, optionally `&requestId=<UUID>` | Show the current authorized observation, or recover one previously submitted command receipt.                                                                                    |
| Command   | `POST /clients/:clientId/objectives/:objectiveId/generation/commands`                                                                                       | Submit an explicit `retry` or `cancel` with the user's reviewed intent and all CAS fields.                                                                                       |
| Pair      | `POST /clients/:clientId/objectives/:objectiveId/generation/confirm-pair`                                                                                   | Submit both explicit retry intents in one Core transaction once both native owners are connected. The response contains two action receipts; it is not a persisted pair receipt. |

The [parser and projection](https://github.com/neo-capiro/capiro-backend/blob/57f8c8047a73df6d4a73351a98a5239f38240a24/apps/api/src/clients/objectives/work/objective-work-command.ts) separate `objective.revision` (currently editable Objective), `requestedSource.revision` plus `requestedSource.canonicalBindingVersion` (ready source for a new command), and `accounting.sourceRevision` (possibly older terminal work). `accounting.outcome` is `failed`, `cancelled`, or `applied` when accounted, otherwise `accounting` is null. The GET also returns `control.version/currentAuthorizationRequestId/cancelledAt`, consent, reconciliation, observation time, and an optional verified `commandReceipt`. A GET observation is not permission to retry, and an old applied accounting source must not be shown as the new requested source.

## Frontend implementation boundary

1. Add a separate strict governed-work adapter for the exact PR #53 GET/command/pair DTOs. Bind every response to the selected client and Objective; display the current Objective revision, requested ready source, historical accounting source, and reconciliation independently. Keep legacy generation and materialization operations intact until the governed path has its actual producers and receiving contract.
2. For each user command, take `expectedObjectiveVersion` from the current authorized Objective, `expectedControlVersion` and `targetAuthorizationRequestId` from that action's control, and `expectedCanonicalBindingVersion` from **requestedSource**. Require ready source for retry. The command body is closed: `schemaVersion:1`, one persisted `requestId` UUID, `command`, `workAction`, those three versions, and nullable target authorization request ID. Pair confirmation shares expected Objective/binding versions and carries distinct persisted request UUIDs and action control/target fields.
3. Persist the exact request ID and payload before the first POST, scoped to actor, tenant, client, Objective, work action, and intent. After a timeout or lost response, query the same action's GET with that request ID and compare the verified receipt; do not silently issue a new request ID. A receipt GET 404 after uncertain delivery does not prove that the POST made no write: keep the original intent and request ID. Handle 409 codes separately: version conflicts require refresh/review; `OUTCOME_UNCONFIRMED` stays unavailable without a new intent; `REQUEST_ID_CONFLICT` stops on a saved-intent integrity mismatch and preserves the original payload. Treat 503 authority or unverifiable-receipt outcomes as unavailable. Never turn `accounting`, `reconciliation`, an expired consent, or a timeout into automatic retry authority.
4. Add an explicit user-facing unavailable state until the native Strategy owner/issuer and Planner effect-owner reconciliation/policy are composed and qualified. Command buttons must remain unavailable when those bindings are absent or uncertain. Do not call the private `/internal/objective-canonical/planner-applications` workload API from the browser.
5. Obtain a reviewed public output-discovery contract before showing canonical results. It needs access-checked current and historical Strategy/Planner outputs scoped to client and Objective, exact requested/accounted source revision and binding version, chosen Strategy type/outcome, queued/running/terminal/uncertain state, and current availability versus creation provenance. Only return browser-safe selectors after custody and permission checks. It must not expose private operation, attempt, run, fingerprint, proof, hash, or owner identifiers. A canonical v3 receiver must distinguish retained and newly created project/task IDs without weakening the legacy decoder.
6. Review a narrow authenticated preview gateway route and policy for these exact Core paths, query keys, methods, body limits, and response schemas. The current preview read allowlist and `CAPIRO_PREVIEW_READ_ONLY=true` do not make the Objective routes reachable. Keep unrelated writes held. Activation needs qualified Core routing, native authority and output discovery, source-matched frontend build, and live denial/recovery checks.

## Ownership and focused acceptance

The frontend owns the adapter, durable request intent, status/action UI, receiver, and narrow gateway review. Core/Planner owns PR #53's authorized observation, CAS, atomic pair command, original-run reconciliation, and bounded public Planner discovery. A named Strategy owner must supply native issuer/reconcile/policy and authorized Strategy output discovery. The browser never supplies owner proof.

Focused checks when implementation becomes possible: each GET variant and `requestId` receipt recovery; changed Objective or control conflict; requested versus accounted source after regeneration; lost-response replay without a second intent; pair half-receipt uncertainty; unauthorized client denial; unavailable/uncertain native owner state; retained v3 outputs and later unavailable outputs. Run broad parity only at a coherent frontend/backend source pin. No browser/build qualification is claimed by this plan.

The PR #53 backend source is draft and its native qualification was in progress at this note. Strategy ownership and public canonical discovery are not yet allocated, so governed commands and canonical receiving cannot be activated from this frontend source alone.
