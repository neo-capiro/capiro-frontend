# PR #48 selected-client read binding review

This source-only successor reviews the three first-chat reads against qualified Core PR #48 source `6542f5b089656b6d255465edd464d06c2a0b408f`. Neo has explicitly permitted preview writes to the existing database. The earlier proposal for a separate `111f269d749cae0249c2141779bd6d7deb93f45c` read-only Core process is therefore not a prerequisite solely to avoid metadata writes. This review changes no service, listener, database role, credential, or deployed image.

The Core middleware verifies the native Clerk bearer, resolves an active tenant membership, and checks JWT tenant/org claims against the selected tenant. The clients controller also requires at least `standard_user`. The frontend proxy obtains its own native `capiro` bearer, fixes `X-Capiro-Tenant: capiro-internal`, strips browser cookies and override headers, and admits only those GET routes and their validated list filters. Fixed operations validate the response at the server gateway; the canonical Portfolio and Meri receivers validate the generic read responses. Neither an environment marker nor a browser client hint supplies authority.

The detail GET can return a tenant-owned archived client, and it does not check a client memory wall. This is suitable for selected-client discovery, but it does not authorize first chat: Core bootstrap separately rejects archived or memory-wall-denied clients and checks actor/client ownership. Live acceptance should exercise those denials. No frontend DTO rewrite is indicated by the PR #48 source comparison.

## Existing database writes on GET

The handler bodies read Core data, but `TenantContextMiddleware` runs first for these routes. For a verified Clerk identity, it may create a missing user, rebind an existing email row to the verified Clerk subject, self-heal a missing active membership from verified org claims, and best-effort update `user.lastSeenAt` on each successful request. Certain authorization denials can append an audit row and emit a security log. Neo's preview database decision permits these existing metadata effects; it does not remove native authentication, tenant checks, or Core's write guards. Do not describe ordinary PR #48 GETs or their database identity as read-only.

## Narrow source and routing successor

The qualified frontend image source `e0b47a34d00b8c181420188ed39a1d849e25ec0a` still requires the `111f` read-source marker. Setting that old marker while routing to PR #48 would falsely identify the backend source. This successor changes only `previewBackendSource` to exact qualified Core source `6542f5b089656b6d255465edd464d06c2a0b408f` and updates the focused test to reject the old marker. The existing `CAPIRO_PREVIEW_READ_ONLY=true` containment, per-route allowlist, native bearer, tenant header, response validation, and no-store behavior stay intact. This is new frontend **product source**: the successful `e0b47a34` / `sha256:185d6ab9f7a8a6395546be4ac2374de2e329ab6182627de18e1fca9732220bcc` image does not contain this change and must not be described as qualified for the PR #48 read binding. A fresh reviewed source pin and separately allocated frontend image qualification are required before activating this successor.

Core's existing first-chat hostname `first-chat-preview.app-dev.capiro.ai` forwards named POSTs at listener priorities 1 and 2, then returns 404 for all other requests under its retained host-only priority-3 guard. A GET rule below that guard will never run. The smallest routing option **that keeps priority 3 unchanged** is a separately reviewed read hostname on the same qualified PR #48 target group and image, with an exact-host + `GET` + anchored path-regex forward below priority 3, followed by a host-only 404 before the host-agnostic production rule. This adds no Core runtime, image, or database role; it does require reviewed DNS, certificate coverage, listener priorities, target health and HTTPS origin. The frontend `CAPIRO_PREVIEW_READ_API_BASE_URL` would be that approved host plus `/api`; do not set a guessed hostname now. An alternative is a coordinated same-host priority reallocation that moves the 404 guard below a new exact GET rule while retaining its deny behavior. Do not change priority 3 without an explicit review of that rule and Meri's other listener allocations.

For either host choice, match only `GET` and the three paths `/api/me`, `/api/clients`, and `/api/clients/<canonical lowercase UUID>`. AWS supports [exact HTTP method and path `RegexValues` conditions](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/rule-condition-types.html). Use anchored expressions, including the frontend's UUID version/variant bounds, rather than `/api/clients/*`; inspect ALB rule limits and normalized-path behavior in the final change set. Keep other methods and paths on a host-specific 404 before production routing. Core still authenticates every forwarded request; the ALB rule is a reachability limit, not an authorization mechanism. No listener change is made by this source successor.
