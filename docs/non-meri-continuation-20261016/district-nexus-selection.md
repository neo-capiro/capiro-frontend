# District Nexus selection lifetime

The current `DistrictNexus.tsx` stored a full `DistrictSummary` in local state. Its canonical `useCapiroQuery` already masks replaced input/API results synchronously and owns abort/reload behavior, but the independent selected DTO survived a state-filter change. Once a new response replaced the map/table, the side pane could still show the old district and metrics. `DistrictMap` only admits clicks from the actual supplied result rows; there is no separate selected-district request or inspected source behavior intentionally allowing a detail outside those rows. The repair therefore follows the existing returned-result selection semantics rather than introducing a broader district query rule.

Selection now retains only `{ scope, districtKey }`, where `scope` is the serialization of the exact existing `intelligence.district.map` request input, including current view, client hint and state filter. On every render, the pane is resolved from current non-loading/non-error returned rows with the matching scope. It never renders a captured old DTO. A scope change or a successful current response that removes the district clears the retained key in the same render; masking does not wait for an effect. Pending/error responses do not become authoritative empty results. Same-scope reloads can resolve the key to the fresh returned row. Picks are accepted only for an actual object in the current returned rows. The state input's uppercase/max-length behavior, map geometry, current-only request, all-client behavior, table order, financial distinctions, Clear all action and canonical query/authentication owner remain unchanged.

Three focused desktop cases are authored in `apps/web/test/browser/district-nexus-selection.spec.ts` using the existing Modules runtime-observed test, operation fixtures, canonical boundary fixture and current 5197 server/config. They cover state-filter replacement with an explicitly held response, scope replacement when two clients return the same district key, and a403 filter refusal kept distinct from an empty map. The first case is a direct regression for the old captured-detail behavior after new map rows arrive. All new fixtures remain local synthetic GETs; no backend, operation, gateway, CSS, shared query or authentication code is changed. The existing Government/location browser spec is not edited.

All three tests are **UNRUN**, including collection. Source checks, formatting, compiler/browser/build validation and architecture binding remain with root/Qualification under the shared capacity hold. No Node, browser, compiler, install, server, provider or database was launched by this repair. No files are staged or committed. Mobile remains deferred.
