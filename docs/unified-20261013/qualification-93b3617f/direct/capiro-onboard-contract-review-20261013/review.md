# Onboard port: independent HTTP contract review

Reviewed `neo-capiro/capirov2` at **`7b5a9644d30d22389b23f0e07f923c8925682047`** against the exact supplied Onboard frontend snapshots. The [matrix](operation-matrix.md) and [machine-readable matrix](operation-matrix.json) cover all **36 operands: 16 funnel, 5 setup, 3 IT, 11 Core, 1 public config**. Source blobs and exact owner links are in [source-pins.json](source-pins.json). This is a static contract review, not acceptance of the evolving port or its gateway implementation.

No repository or index was changed. No application, service, provider, signup, billing, invitation, IT, test, build, install, or browser execution occurred. GitHub reads obtained pinned owner source only. Controller/service semantics were inspected, not copied or imported into the frontend; this packet contains references and derived contract descriptions, not another implementation.

## Required distinctions for the port

1. **Firm memory saves are review submissions.** Native `memory.controller.ts:214–259` returns `{status:'pending_review',candidateId,activeItemUnchanged:true}` for firm/client scopes. The former Onboard interface promised `{ok:true,updatedAt}` and `AiSettingsOverlay.tsx:90–104` then marked the file covered and could complete the task. Preserve the draft and show submitted-for-review; do not claim active memory changed. GET sections returns active sections plus `pendingReview:null|{candidateId,status:'pending_review',submittedAt}`. That read returns the newest file proposal, not a body echo or proof the current actor's submitted text is active. The three firm types are `firm-soul`, `firm-compass`, and `playbook`; arbitrary type/slug forwarding would broaden the operation. [Native controller](https://github.com/neo-capiro/capirov2/blob/7b5a9644d30d22389b23f0e07f923c8925682047/apps/api/src/memory/memory.controller.ts#L214), [pending metadata](https://github.com/neo-capiro/capirov2/blob/7b5a9644d30d22389b23f0e07f923c8925682047/apps/api/src/memory/memory-candidate.service.ts#L242).

2. **Setup read and write enums differ.** Reads can report `skipped`; transition DTO `from` and `to` permit only `none|waiting|verifying|done`. `invites → done` is separately rejected: completion owns that transition. A 409 is a failed compare-and-set and needs current-state reconciliation, not a silent retry with a new `from`. The Google capability skip route owns deferred IT status. [Controller](https://github.com/neo-capiro/capirov2/blob/7b5a9644d30d22389b23f0e07f923c8925682047/apps/onboard-api/src/setup/setup.controller.ts#L15), [CAS](https://github.com/neo-capiro/capirov2/blob/7b5a9644d30d22389b23f0e07f923c8925682047/apps/onboard-api/src/setup/setup.service.ts#L181).

3. **Preserve actual response nullability and available identity.** Native funnel sessions include `sessionId`, `failureReason`, and best-effort `stripe` statuses, omitted by the old frontend interface. Purchaser names/org name are nullable; `itAdminEmails` is an array. SetupIntent `clientSecret` is nullable. Subscription `clientSecret` and `hostedInvoiceUrl` are optional and nullable. A missing secret cannot mount a usable payment form; missing Stripe snapshot fields cannot mean paid. Receipt schemas must accept these native states without inventing success. [Session shape](https://github.com/neo-capiro/capirov2/blob/7b5a9644d30d22389b23f0e07f923c8925682047/apps/onboard-api/src/funnel/funnel.service.ts#L41), [payment results](https://github.com/neo-capiro/capirov2/blob/7b5a9644d30d22389b23f0e07f923c8925682047/apps/onboard-api/src/funnel/funnel.service.ts#L802).

4. **Do not infer provider availability from missing metadata.** Native IT reads return both provider booleans. The old `ItAdminPage.tsx:98–100` fallback turns Microsoft on when `providers` is absent; that is not a native guarantee. Require current successful capability metadata, keep false/missing/unavailable distinct, and preserve the explicitly deferred versus connected state. A 503/network failure is not proof an invitation expired. `funnelEnabled` is public availability configuration, not server authorization. [IT read](https://github.com/neo-capiro/capirov2/blob/7b5a9644d30d22389b23f0e07f923c8925682047/apps/onboard-api/src/it-admin/it-admin.service.ts#L137).

5. **Preserve merge and effect semantics.** `setOrg` keeps omitted optional profile fields and appends normalized IT contacts; it exposes no clear/remove operation. Manual client creation returns a real client while enrichment remains detached; import is per-row and per-chunk, not atomic across the selection. A team invitation receipt means invited, not accepted or delivered. Setup completion permits optional firm AI and starts the trial clock once; it is not proof all invitations were delivered. Existing plan/runbook descriptions contain historical gaps (for example the plan's missing LDA slot enforcement); pinned controllers/services take precedence over those old implementation notes.

## Authentication and signed-out composition

- **Funnel:** use the default Clerk session token (`getToken()`), without requiring an organization or Core identity. Native ClerkUserGuard verifies the purchaser subject; it does not require or forbid an organization. Org-less users must reach registration/verification. A missing token must fail locally/401, not fall through to anonymous authenticated operations. Only GET funnel/session's 404 is normal unregistered state.
- **Setup:** also use the default session token. Native TenantGuard resolves the canonical org/tenant and active membership; mutations additionally require exact Clerk org-admin role and an onboarding-v1 tenant. Never use a client hint, unverified JWT decode, raw org id, or `role.includes('admin')` as authority. A legacy tenant's `complete:true` is a switch-context notice, not permission to edit it.
- **Core:** use the designated `capiro` template token. Reuse existing canonical identity and fixed-operation owners. GET me has no extra route role annotation; firm reads/memory catalog use member minimum; firm anchor/import/memory writes and team invitation use admin rules. Native manual client POST inherits `standard_user`, despite a broad nearby comment suggesting admin mutations; do not misdescribe that contract or change backend authority in the port.
- **Public config and IT:** preserve signed-out reachability. Config explicitly omits credentials. IT uses the emailed capability token, not a Clerk account; native syntax is 64 lowercase hexadecimal characters and invite expiry is seven days. Do not put the public IT page behind the authenticated tenant/client application boundary. Treat token replacement as a new view lifetime; never forward browser-supplied Authorization/cookies or leak the token in logs/analytics.
- Protected requests/results/drafts must be scoped to the current actor, session, organization, operation inputs and, when supplied, funnel `sessionId`. Dispose late results after replacement. Cached success during failed/refetching reads cannot authorize a fresh payment/invite/import or revive expired scope. Most native acknowledgements omit actor/tenant/session echoes; correlation is local transport lifetime plus authoritative current reads, not a fabricated required echo.

## Downloads and navigation policies for the fixed gateway

**Signed PDF:** native Content-Type is `application/pdf`; names are exactly `Capiro-Terms-of-Service-signed.pdf` and `Capiro-Subscription-Agreement-signed.pdf` (`signed-pdf.service.ts:45–54`). The signed controller regenerates bytes for the current purchaser, but publishes no response length ceiling or document digest. The old browser helper buffers without a bound and uses a loose Content-Disposition regex. Reuse the existing bounded binary owner: require PDF MIME, cap streamed bytes even without Content-Length, reject empty/oversized responses, set a registered safe `.pdf` filename and `nosniff`, use no-store, and revoke/discard local object URLs after use or authority change. The chosen maximum is a frontend resource policy, not a native guarantee; document it and do not blindly copy the API's unrelated 2 MB JSON request limit.

**IT OAuth:** returned URLs are exactly built for `https://login.microsoftonline.com/organizations/adminconsent` or `https://accounts.google.com/o/oauth2/v2/auth`. Validate protocol, exact origin/path, no credentials, and expected provider; preserve opaque server state and fixed callback route. The nested `redirect_uri` points to the configured native public API origin plus `/onboard-api/it/{provider}/callback`; do not rewrite or synthesize the state/callback in the frontend. The callback is native-owned, outside these 36 operations. A consent URL only starts authorization and does not prove connection. Google provider configuration requires both native client id and secret, with client id public in the invite response. [URL construction](https://github.com/neo-capiro/capirov2/blob/7b5a9644d30d22389b23f0e07f923c8925682047/apps/onboard-api/src/it-admin/it-admin.service.ts#L159).

**Stripe:** use the published Stripe UI flow for card/ACH confirmation; the old flow uses `redirect:'if_required'`. Never proxy an arbitrary confirmation URL or expose client secrets in logs/storage. The backend forwards Stripe's nullable `hosted_invoice_url` without publishing an allowed-origin schema. Therefore an approved exact hosted-invoice navigation policy/configuration is still needed before enabling that link; HTTPS alone or a broad `*.stripe.*` suffix is insufficient. Retain query/path tokens without leaking them. Wire `advanced:true` means invoicing can proceed, and ACH can advance during processing; neither is a settled-payment receipt. Client-confirmed SetupIntent id must stay tied to its actual method and current purchaser.

**Configuration:** ignore `apiBaseUrl` as a browser-controlled gateway destination. Fixed operations resolve only server-configured service origins. Do not forward arbitrary paths, methods, headers, redirect targets, or the native team invitation `redirectUrl` field merely because the owner DTO supports it. Internal port navigation belongs to root's approved routes; public sibling-host config is not authority to move the authenticated session. Preserve native redirect rejection/deadlines/no-store behavior in the shared gateway.

## Retry, ambiguity, and receipt acceptance

| Operation family | Native guarantee / required UI interpretation |
| --- | --- |
| Setup task transition | True compare-and-set on current task/from. Bind task and returned status; 409 means reconcile, not replay. |
| Provision | CAS `org_setup → provisioning`, repeated in-progress/provisioned calls report status. Timeout/502 can follow partial tenant/provider effects. Poll status; failed state requires native operator recovery, not a new signup loop. |
| Setup complete | Trial timestamp is conditional and not restamped. Still confirm current returned `complete`/tasks; no mail-delivery claim. |
| SetupIntent / paid subscription | No browser idempotency key. SetupIntent creates each time. Subscription reuses a stored live subscription but cancels/replaces an incomplete one, and creation precedes durable session storage. No blind POST retry after unknown outcome. |
| Legal accept | Validates displayed active versions; read-before-insert deduplicates session/doc/version. Receipt is only `{ok:true}`, not a new signed-body echo or email-delivery proof. Keep uncertainty after loss and recover with current session/signed document. |
| IT create/resend / team invite | Sends/creates/revokes or rotates links. Unknown response can follow real effects. Preserve draft and unknown state, refetch authoritative metadata where available; do not automatically resend. |
| Manual client creation | No supplied idempotency key; creates a row. Unknown result can duplicate if retried. Receipt needs valid current-context client identity, not just any 2xx. |
| LDA import | Deduplicated ids/current registrant, per-id locking/duplicate skip; before-batch 402 versus mid-batch skips. Preserve completed chunks and per-id outcomes; loss is not total rollback and a subsequent cap refusal does not prove no prior import. |
| Firm memory submission | Pending candidate id, active item unchanged; no CAS/version input. Validate specific pending receipt, retain draft, and do not collapse pending proposal into active save. |

All mutations need synchronous same-attempt double-submit protection and current-authority result checks; cancellation of a browser request is not rollback of a durable effect. Validation failure, timeout, malformed/foreign acknowledgement, or aborted response must not be presented as definite non-execution. Do not infer receipt fields the service does not return: most funnel setters and IT acknowledgements are only `{ok:true}`; status and paid-status omit a session/subscription id. For available identifiers, use exact context checks: sessionId, selected registrant, task/to, requested import ids, requested memory type/slug, normalized invitation email/role, and selected PDF kind.

## Concrete missing public artifacts and limits

1. The supplied artifact set has no versioned exported Onboard HTTP request/response schema for these 36 operations. Owner input DTOs are controller-local; old frontend interfaces use unchecked casts and demonstrably drift. A reviewed local HTTP boundary can validate the pinned native contract, but must not masquerade as a backend-published package or import private controllers/services. Root reports the existing PR16 public artifact `38fec5c8` exports pricing constants; that separate entry still needs its own exact qualification and is not an Onboard HTTP schema.
2. No public client idempotency/recovery-key contract exists for SetupIntent/subscription/manual-client/invitation creation, nor a comprehensive receipt binding every mutation to actor, tenant, request version and input digest. Native-specific recovery above is the available boundary; generic safe replay/exactly-once acceptance cannot be claimed.
3. No native signed-PDF response cap/hash/version receipt or public hosted-invoice origin allowlist was found in the reviewed surface. Apply explicit gateway resource/navigation policy and label its ownership; do not invent a native guarantee.
4. Firm memory GET exposes active sections plus proposal metadata, not the candidate's proposed sections or a revision suitable for optimistic compare-and-set. The 36-operation set contains no candidate decision operation. Review submission can be represented honestly; immediate activation/approval and conflict-safe editing cannot be manufactured by the port.
5. Native provisioning is a multi-service workflow with partial-failure states and operational recovery; source inspection does not prove durable native recovery, effect delivery, endpoint configuration, provider activation, redirects, real Clerk session/org behavior, actual PDF bytes, or live billing. Historical deployment status in owner runbooks was not revalidated. Those live effects were explicitly excluded from this review.

The two concrete schema/behavior mismatches (memory review receipts and transition `skipped`) and the nullable/native identity/provider-availability details were sent directly to both root and the feature owner. Root owns shared integration, final schemas, navigation policies and qualification. No blanket capability denial is recommended: expose the operations whose current contracts support the intended behavior, with these precise limits.
