**Recommended entry:** use the existing Meri **Files** destination at `/meri/files`, mirrored in the existing mobile Meri navigation. The first workspace should offer typed DOCX creation, explicit full-replacement revision of an exact returned version, inspection and verified download. It should show only versions actually received in that workflow. PR50 provides no list/search/history enumeration API: do not create a library, fabricate a file inventory or imply durable rediscovery.

The new document requests, nested version/inspection/execution receipts, error vocabulary and binary response metadata are not a supported frontend export. A separately versioned public receiving/request projection from canonical owners is required before the production adapter. Do not import private artifact code or hand-maintain a duplicate DTO/validator.

## Exact advertised HTTP surface

All four are POST JSON with `Authorization: Bearer <existing opaque action session>`; native Clerk JWTs and artifact capabilities are not these request credentials.

| Path | Exact outer request | Success |
| --- | --- | --- |
| `/api/documents/create` | `{deliveryId,request}` | `{version,inspection,execution}` |
| `/api/documents/revise` | `{deliveryId,baseVersionId,request}` | `{version,inspection,execution}`; a new immutable version with exact retained parent |
| `/api/documents/inspect` | `{versionId}` | `{version,inspection}` |
| `/api/documents/download` | `{versionId}` | Verified bytes, canonical ASCII attachment filename and MIME |

`request` is the backend-owned `WordRequest`, with `operation:'create_word'`, `format:'docx'|'txt'`; DOCX paragraphs use `{kind:'paragraph',runs:[{text:'Draft text'}]}`. The README mentions titles, tables, runs and supported image/chart references but is not a complete browser schema. PDF is explicitly excluded. A DOCX-only initial UI is a deliberate bounded subset; TXT need not be exposed merely because the backend admits it. Image/chart references require supported asset contracts and are outside a plain text first editor. Do not infer complete nested field names, limits, identifier syntax or allowed asset inputs from prose examples.

Revision is a complete typed replacement based on an exact version, not an in-place save or natural-language model call. The application introduces no approval choice or renderer. Filing is a separate approved command and is not supplied by these routes. Existing session issuance may be mounted beside the document application on the same trusted host; sharing the session protocol does not prove the live service grants document execution.

Responses advertise `Cache-Control:no-store` and `X-Content-Type-Options:nosniff`, without CORS permission. Errors are only `{error:{code,outcome}}`. Documented statuses include session denial403, disabled503, timeout408, cancellation499, other owner failure502 and size413. Malformed route/body/media is refused before effects. Started uncertain writes are `UNKNOWN`; completed output denied at release is `RESULT_NOT_RELEASED`; unsuccessful reads are `READ_UNAVAILABLE`. These are not rollback/cancellation/retry proofs. The same delivery is not regenerated; historical reconciliation remains backend-owned. The documented 15000ms/131072-byte request/1048576-byte response configuration is an example, not a deployment-qualified browser limit.

## Minimal composition and existing owners

- Keep the Next route thin; a cohesive Meri document feature owns draft input, chosen returned version and explicit create/revise/inspect/download interactions. The trusted backend retains artifact generation, immutable storage, accounting, current authorization, run/context/grant binding and reconciliation. No parallel model loop, storage service or approval UI.
- Reuse the existing session/bootstrap grammar, canonical selected-client/ApplicationBoundary lifetime and bounded transport foundations. `ActionHostController` currently constructs `GovernedActionWorkflow` directly, so it is not a drop-in document port. Root should coordinate the smallest shared session-lifetime seam justified by the two real callers; document errors, delivery fencing and binary reads remain distinct from recommendation commands.
- A root-owned fixed same-origin document proxy may preserve the four exact routes and opaque bearer. Do not route document bytes through `receiveActionResponse` or the JSON-only response helper. Downloads need bounded streaming bytes, cancellation/deadline handling, exact expected version/hash/length/MIME/filename correlation, and object-URL disposal before offering a download. No raw storage URL is a substitute.
- Keep credentials and draft/version content in the live feature/session lifetime, not URLs, logs, persistent browser storage or QueryCache. Retain only the necessary non-secret uncertainty metadata across same-cache navigation. The delivery fence must be set synchronously before dispatch; canonical identity/client/cache replacement must retire it without old completions recreating cache state. Do not reuse the recommendation operation's journal key or treat it as document reconciliation authority.
- Desktop `Sidebar.tsx` already has the disabled Files label and icon. `MeriMobileNavigation.tsx` supplies the narrow-screen fallback. Both currently identify Conversations by “not actions”; adding Files requires exact destination matching so only one link has `aria-current='page'`. Preserve verified client hints, Back/Forward behavior and canonical selected-client gating. Coordinate against the final navigation/accessibility successor, not an obsolete snapshot.
- `ProductShell` currently distinguishes disconnected samples from recommendation actions through an action-specific boolean/footer. A document entry needs truthful document availability text under the same shell owner, not a copied shell or a footer claiming recommendation behavior. No existing Files-specific Figma target was assessed in this contract review; capture/review the appropriate existing design evidence before implementation.

## Public handoff needed and scope decisions

1. Publish a versioned browser-safe document export: canonical request types/validator, exact success and finite status/error receiving schemas, detached/frozen receiving behavior, source/hash metadata and an immutable package artifact. Include delivery/version ID grammar and create/revise/inspect request/receipt correlations. Preserve existing0.1.1 recommendation exports and frozen event consumers.
2. Specify the download receiving contract: authoritative expected version/object hash and byte length, MIME/ASCII filename rules, required HTTP metadata/status, maximum buffered/streamed bytes and how errors differ from binary success. Server verification already exists; frontend must not invent a hash header or field the public wire does not expose.
3. Specify delivery-ID ownership and interrupted-write reconciliation. The HTTP body carries a deliveryId but this README does not define safe remount/recovery allocation policy. A lost create acknowledgement may leave a real immutable version whose ID is unknown to the browser; no listed endpoint discovers it by deliveryId. A new delivery must not become an accidental retry.
4. Version reopening is deliberately limited: no listing, latest-version, parent-chain enumeration or reconciliation endpoint is documented. An explicit known-version-ID lookup can use inspect if the product owner wants it; it is not required for the first workflow and must not imply authority. Do not infer a stale-parent branch policy beyond explicit backend refusal and the exact parent selected by the user.
5. Keep the initial UI a typed plain-text DOCX drafting workspace. Rich tables/assets, natural-language drafting, upload, PDF, Office preview, rename/delete/share/search, filing and Commitments are not granted by this increment. A local inspection summary is not native Word rendering or visual acceptance.
