# Portfolio 3.4: design decisions and source wiring

Native Figma renders below are 1440 × 1040 PNGs. These are comparison evidence, not application assets. The user's current product direction places Meetings in the Portfolio client profile and Outreach in Modules, with no extra reports or tabs. That resolves the feature location; it does not select between the conflicting mastheads or intake layouts below.

| Files storage                  | [Normal `1064:167100`](https://www.figma.com/design/mpXWnySldUFzdVna8i69Ki/Capiro-3.4-Portfolio?node-id=1064-167100) ([PNG](files-1064-167100.png)); [over allowance `1064:167588`](https://www.figma.com/design/mpXWnySldUFzdVna8i69Ki/Capiro-3.4-Portfolio?node-id=1064-167588) ([PNG](files-over-quota-1064-167588.png)) | The design shows **7.4 MB of 10 GB**, then **10.4 GB of 10 GB** with an over-allowance warning. The denominator is an existing product policy constant (`CLIENT_STORAGE_QUOTA_BYTES` in `capirov2/packages/shared/src/index.ts:711`; 10 GiB in bytes, labeled 10 GB in Figma), currently reported rather than enforced. The current frontend reads `engagement/attachments?clientId=…` and receives only attachments visible to the reader; `byteSize` can be null. It has no authoritative client-wide used-byte aggregate. Summing visible rows would undercount hidden/unknown bytes and cannot prove an overage. Provide a scoped usage source and a Figma usage-unavailable state; do not invent usage or imply uploads are blocked.                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Quick Log: general             | [Client form `1064:154447`](https://www.figma.com/design/mpXWnySldUFzdVna8i69Ki/Capiro-3.4-Portfolio?node-id=1064-154447) ([PNG](quick-log-client-1064-154447.png))                                                                                                                                                         | The design includes Note, Call, Meeting, Email, Commitment; **When** and optional **Objective**; plus an optional Planner follow-up. Core already permits manually recorded commitment and optional `occurredAt`, with meeting owned by Calendar. The direct Core activity path now accepts commitment and an edited `occurredAt`; fixture-backed browser checks passed direct save, receipt validation, and verified Undo. Note/call/email/decision/request and Calendar meeting entry remain. The generic follow-up UI and browser-fixture recovery are retained, but live Core completion is unverified because the checked `capirov2` revision has no `activity-commands` route. The combined follow-up command accepts only its older activity fields, so the UI explains and disables a combined follow-up for commitment or custom activity time. An objective link and automatic Meri selection need a client/objective binding contract. The Member destination already uses its separate scoped Directory note flow; do not route it through client activity commands.                                                                                                                 |
| Quick Log: commitment and task | [Commitment + task `1064:154792`](https://www.figma.com/design/mpXWnySldUFzdVna8i69Ki/Capiro-3.4-Portfolio?node-id=1064-154792) ([PNG](quick-log-commitment-1064-154792.png))                                                                                                                                               | Core allows `dueAt` on commitment/request, and the direct frontend save now sends and verifies it. [The 1440 × 1040 Playwright capture](../playwright/quick-log/commitment-direct-1440x1040.png) shows the available commitment fields and the disabled combined follow-up; direct save and Undo, refusal of a mismatched due-date receipt, and [blank When save-time behavior](../playwright/quick-log/blank-when-1440x1040.png) passed 3/3 fixture-backed browser checks. The design also asks **Who owes it**, **Counterparty**, optional **Objective**, a custom Planner **Task** title, and a **Strategy step** link. Core's activity create DTO has no direction, counterparty, objective, or strategy field. The existing combined follow-up command accepts assignee plus optional due date/time/zone, but no commitment, custom activity time/due, custom task title, or strategy link. An atomic commitment plus follow-up and the other richer fields need owner contracts and permission semantics before they can be saved together. A required activity title remains in the live API although the mock form shows only “What happened”; do not silently discard that requirement. |
